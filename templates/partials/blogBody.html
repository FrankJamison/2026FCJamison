A 2006 Time Capsule: FrankJamison.com

Every developer has an origin story. Some start with a bootcamp. Some with a framework tutorial at 2 a.m. Mine? A raw, caffeinated plunge into HTML and CSS in 2006—when rounded corners were a luxury, gradients were loud, and tables were still hanging around like uninvited guests at a LAN party.

This project is a preserved snapshot of that era: the original 2006 FrankJamison.com. Not a remake. Not a refactor. This is the artifact itself—rough edges, earnest ambition, and all.

Back then, the web felt smaller and more personal. You didn’t install a stack; you opened a text editor and started typing. This site grew line by line, fueled by curiosity and a stubborn need to understand how the pieces fit together. Layouts were hand-built. Styles were trial-and-error. JavaScript was used sparingly, because breaking things was easy and debugging tools were… aspirational.

And yet—there’s something beautiful in that simplicity.

This project matters because it shows the long arc of learning. Before frameworks. Before pipelines. Before “best practices” hardened into doctrine. It captures the mindset of a developer at the very beginning: experimenting, breaking things, fixing them, and learning by doing. The design choices reflect the mid-2000s web aesthetic—bold colors, structured layouts, and a clear desire to make something real and public.

Looking at it now, with modern eyes, it’s tempting to critique. But that misses the point. This site isn’t here to compete with modern standards—it’s here to document growth. It’s proof that progress doesn’t start polished. It starts messy, curious, and slightly chaotic.

In a portfolio full of recent projects, this one plays a different role. It’s the prologue. The “level one character with questionable stats.” The reminder that every clean, responsive, well-architected build stands on a pile of early experiments that dared to exist.

So this project stays exactly as it is. No modernization. No cleanup. Just a preserved moment from 2006—when the web was weird, learning was manual, and the spark first caught.

And honestly? I wouldn’t reroll it.

Building Time: The 2006 Analog Clock Project

Some projects are about scale. Others are about speed. This one? This one is about precision—the quiet, relentless ticking of logic doing exactly what it’s supposed to do.

The 2006 Analog Clock Project is a deceptively simple web application that recreates a classic analog clock using modern front-end techniques. No libraries doing the heavy lifting. No shortcuts. Just JavaScript, CSS, and the stubborn belief that understanding fundamentals is never a waste of time. (Unlike meetings that could’ve been emails.)

Why an Analog Clock?

Because analog clocks are brutal in the best way.

They demand:

  • Continuous motion
  • Trigonometry hiding in plain sight
  • Real-time synchronization
  • Visual accuracy down to the degree

Digital clocks forgive you. Analog clocks expose you.

This project was an exercise in translating time as data into time as motion—turning hours, minutes, and seconds into rotating hands that never drift, stutter, or lie.

Under the Hood

At its core, the clock runs on JavaScript’s Date object, polling the current time and converting it into rotational values.

Each hand:

  • Seconds rotate at 6° per second
  • Minutes rotate at 6° per minute (with second-based offsets for smooth motion)
  • Hours rotate at 30° per hour (plus minute offsets, because accuracy matters)

CSS handles the transforms, anchoring each hand at its base so rotations feel natural—no helicopter blades here. Subtle transitions keep motion smooth without introducing lag, because a clock that jitters is existentially unsettling.

Design Philosophy

The visual design stays intentionally restrained.

This isn’t about flashy gradients or glassmorphism flexing for attention. It’s about clarity, contrast, and balance. The face is readable at a glance. The hands are distinct. The clock looks like a clock—an underrated achievement in web design.

Dark backgrounds were chosen to reduce visual noise and keep focus on motion, reinforcing the idea that time should flow, not shout.

What This Project Proves

This project demonstrates:

  • Comfort with JavaScript timing and real-time updates
  • Practical use of CSS transforms and positioning
  • Attention to mathematical detail
  • Respect for classic UI metaphors
  • An understanding that fundamentals scale better than frameworks

It’s also a reminder that not every portfolio piece needs to be a sprawling app with fifteen dependencies and a build step that could summon ancient spirits.

Sometimes, mastery looks like restraint.

Final Thoughts

The 2006 Analog Clock Project is a quiet project—and that’s its strength. It ticks along faithfully, doing one thing well, every second, without complaint. Honestly? Goals.

Time is relentless. Code doesn’t have to be.

And if you can make something as unforgiving as an analog clock behave perfectly in the browser, you’re probably ready for much bigger monsters.

Next project. Same discipline. Fewer mercy rolls.

Hello, World (But Make It Intentional).

Every portfolio has a beginning. This is mine.

I’ve spent years working at the intersection of structure and creativity—teaching mathematics, supporting learners with wildly different needs, troubleshooting systems when they fail at inconvenient times, and quietly building things after hours just to see if I could make them work. Somewhere along the way, code stopped being a curiosity and became a language I wanted to speak fluently.

This site exists to document that journey.

Not as a highlight reel—those are easy—but as a living record of growth. The experiments that worked. The ones that didn’t. The bugs that taught me more than the tutorials ever did. The small wins that stack into real momentum.

Why Software Development?

Because software rewards clarity.
Because systems thinking feels like home.
Because solving a problem once—and solving it well—is a kind of quiet magic.

Coming from education and technical support, I’ve learned how people actually interact with systems, where they get stuck, and how fragile confidence can be when technology doesn’t behave. That perspective shapes how I approach development: practical, empathetic, and relentlessly user-focused.

What You’ll Find Here

This blog will evolve alongside my skills. Expect posts about:

  • Projects I’m building (and rebuilding)
  • Front-end and back-end experiments
  • Lessons learned the hard way
  • Design decisions and tradeoffs
  • The occasional rant about why something should be simpler

If you’re here to skim code, great.
If you’re here to understand how I think, even better.

Where This Is Going

The goal isn’t perfection. It’s progress.

Each post is a marker on the road—proof that I’m moving forward, refining my craft, and taking ownership of the work I put into the world. I believe good developers aren’t just problem solvers; they’re communicators, learners, and builders with taste.

This blog is part of that practice.

Thanks for stopping by.
The next post will be more technical. Probably less poetic.
But no promises.
