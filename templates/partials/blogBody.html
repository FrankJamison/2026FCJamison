FrankJamison.com:
A Personal Web Presence, Structured by Craft

What you’re looking at with the 2013 version of FrankJamison.com isn’t a template, a boilerplate, or a modern static-site generator project. It’s a real, preserved legacy personal site from 2013, intentionally kept static, no build tools, no frameworks — just classic web fundamentals tuned for real browsers and real humans.

In a world where projects spin up with React/Vite in minutes, there’s something grounding about code that was written to work everywhere, from old desktop browsers to modern phones. Let’s unpack both how it works and why it matters technically.

What This Project Actually Is

At its heart, the 2013 version of FrankJamison.com is:

  • A static, multi-section personal site — home, portfolio, writing archives, galleries, music, poetry, resume, and contact form.
  • Written in classic HTML / CSS / JavaScript with no dependency on modern build systems.
  • Includes a working PHP contact form that talks to SMTP instead of relying on mail() — important for real-world reliable email handling.
  • Preserves legacy tech like a Flash banner by embedding it via Ruffle (a WebAssembly Flash emulator) so it still runs in modern browsers without plugins.

This isn’t a museum piece glued together; it’s maintainable and runnable today. It even includes instructions for local virtual host configuration.

Architectural Overview

Directory Layout & Static Pages

The repository follows a traditional folder structure:

  • index.htm — main landing page
  • resume/, portfolio/, gallery/, music/, poetry/ — sectioned content folders
  • contact/ — contact form and server integration
  • resources/ — shared CSS, JS, images, and Ruffle assets

There’s no index.html by design — it’s index.htm, a choice that harks back to early web servers and compatibility considerations.

Shared UI, the Old-School Way

Instead of components or includes at build time, this site uses runtime JavaScript includes to import repeated UI elements (header, menu, footer). The core pattern:

  • menu.js — primary nav
  • resumeMenu.js — side nav for resume section
  • header.js — sets up the Ruffle instance to play the Flash animation
  • footer.js — shared footer markup

These scripts use DOM methods like document.write() to inject HTML. Yes, that’s frowned upon today, but in 2013 it was a standard way to centralize shared layout before templating engines were mainstream.

Preserving Legacy Flash with Ruffle

One of the coolest parts living in this repo is the Flash banner:

  • Original .swf file lives at: resources/sfw/header.swf
  • Loaded in the browser using the bundled Ruffle WebAssembly build found in: resources/ruffle/

This is a real-world example of running historically obsolete content using modern browser tech — a great case study in graceful degradation and forward-facing compatibility layers.

Contact Form: PHP + SMTP

Instead of mail(), the site uses SMTP with authentication — much more reliable on shared hosts.

Configurable via:

  • Environment variables (preferred)
  • A local smtp_settings.php (gitignored)

The code even logs failures to contact/sendmail_failures.log, a simple but pragmatic debugging pattern.

Technical Considerations for Modern Maintenance

Absolute Root Paths

The site uses absolute-root URLs like /resources/... and /resume/.... That’s fine for a root deployment, but it breaks under subpath hosting unless you rewrite paths — a classic gotcha when migrating legacy static sites.

Character Encoding

Most pages declare charset=iso-8859-1. This is unusual today, where UTF-8 is the de facto standard. Keeping this consistent avoids mangled text (mojibake) in older content.

GitHub Metadata
  • No description or topics are set for the repository, which lowers discoverability.
  • No releases, stars, or forks — but this is intentional; it’s a portfolio preservation project, not a deployable piece of infrastructure.

Why Developers Should Care

Even if you’ll never write HTML like this again, this project is a miniature case study in:

Web Fundamentals
  • Static pages tuned for browser compatibility
  • Manual DOM manipulation for shared UI
  • Handling server interactions with minimal backend code

These are skills that still matter when you’re debugging legacy systems, optimizing performance, or doing a quick proof-of-concept without a toolchain.

Legacy Tech Integration

Ruffle + WebAssembly is an elegant, real example of emulating obsolete tech in a modern runtime — something increasingly relevant with archived games, animations, or legacy UIs.

This repo isn’t just a snapshot; it’s an exemplar of incremental preservation — keeping old tech alive without reinventing the wheel.

TL;DR for Devs

  • Classic static web project from 2013 with modern maintenance touches.
  • JS includes instead of templating engines.
  • Flash preserved via Ruffle (WASM).
  • PHP SMTP instead of mail().
  • Absolute root paths and iso-8859-1 encoding warrant careful handling.

Globe Bank:
Global Finance, Structured by Design

The Globe Bank project is a throwback to the era when financial institutions presented themselves on the web with calm authority and no unnecessary flourishes — and it backs that design with a real database-driven system rather than a static mockup. This project lives in the sweet spot between historical aesthetic and functional engineering, showing how early CMS-style sites were built with practical PHP, MySQL, and thoughtful routing.

At its core, the Globe Bank project isn’t just pixels on a screen — it’s a working content management system where site content, navigation subjects, and pages are stored in a database and rendered dynamically for both visitors and authenticated staff.

Design Philosophy: Quiet, Balanced, Predictable

The visual design respects the expectations of a global finance interface from the late 2000s:

  • A grid-based structure that reinforces clarity and hierarchy
  • Typographic choices that prioritize legibility over flair
  • A subdued palette (think blues and neutrals) that evokes trust and stability
  • Navigation that’s intuitive rather than clever, because in financial contexts, familiarity isn’t boring — it’s reassuring

This kind of design communicates one thing clearly: you can rely on this interface to show you what you need, without noise or distraction.

The interface doesn’t surprise the user with animations or unexpected layouts: it’s about function over flash, a reflection of how users expected bank sites to behave in that era.

Tech Stack: PHP, MySQL, and Intentional Simplicity

GlobeBank is implemented using a classic LAMP-style stack:

  • PHP for server-side logic, using mysqli to communicate with the database
  • MySQL / MariaDB as the content store
  • Server-side sessions for staff authentication and secure access control

    • This isn’t a modern framework — it’s the real deal: raw PHP with structured code organization that separates public site rendering from admin interfaces.

    Instead of bundling CSS and JS frameworks, the project keeps dependencies minimal, focusing on:

    • Semantic HTML
    • Clean, purposeful CSS
    • Minimal JavaScript only where interactions benefit the user

    These choices keep the system fast, clear, and easy to maintain, which was critical in an era of varied connection speeds and browser capabilities.

    Real Database Integration: Making It Functional

    One of Globe Bank’s strengths is that it isn’t a static brochure — it’s backed by a MySQL database with real schema files included (setup_database.sql). The database contains structured tables such as:

    • subjects: which represent navigational sections
    • pages: which hold the actual content displayed publicly
    • admins: for staff access control

    Through this database, the site can:

    • Dynamically generate navigation
    • Render pages based on database content
    • Allow authenticated staff to add or edit content

    This is a true content management experience, albeit simple and focused, demonstrating how early CMS systems delivered flexibility without the overhead of modern frameworks.

    Routing and Site Structure

    The project uses a thoughtful approach to routing that reflects the flexibility needed in different deployment environments:

    • A root index.php file redirects into public/, where the public-facing site lives
    • The application computes a root directory dynamically, allowing the site to work whether the public/ directory is the web root or not
    • A structured private/ directory contains database connections and shared templates that are not directly web-accessible

    This separation between public code and internal logic enhances security and mirrors good practice even by modern standards.

    Staff Area: Authentication and Administration

    The staff area is password-protected, providing:

    • A login screen
    • An admin menu
    • Pages to manage content such as subjects and pages

    The authentication logic leverages PHP sessions and bcrypt-hashed passwords, with clear guidance on originating a first admin account by inserting a hashed user directly into the database — a practical approach for early dev workflows.

    Why This Project Matters

    The Globe Bank project is more than a historical reconstruction — it’s an honest, functional example of how database-backed PHP sites powered real content in the late 2000s. It shows that:

    • Structured, predictable design supports user trust
    • Database integration enables durability and reuse
    • Clean, minimal stacks can still be expressive and purposeful

    As a portfolio piece, it speaks to both design sensibility and practical backend engineering, highlighting a thoughtful grasp of how sites were built — and how foundational skills still matter today.

    No smoke. No mirrors. Just data.

    What it does

    • Total time elapsed
    • Characters typed versus characters correct
    • Accuracy as a first-class metric, not an afterthought
    • Words per minute calculated from real input, not optimistic guesses

    The results update cleanly and clearly, giving you feedback that’s useful without being condescending. You don’t get a gold star. You get numbers. Cold, beautiful numbers.

    Design philosophy

    The interface stays intentionally minimal. Typing tests live or die by distraction—or the lack of it. Fonts are readable. Spacing is forgiving. The focus stays where it belongs: the text you’re typing and the rhythm of your hands.

    There’s a quiet, almost meditative quality to it. Until you miss a character. Then it becomes personal.

    From a development perspective, this project emphasizes fundamentals:

    JavaScript handles real-time input evaluation, timing logic, and metric calculation without external libraries doing the heavy lifting. State management is explicit and readable, making it easy to reason about what’s happening at any moment during the test. The structure favors clarity over cleverness—future-proofing by being understandable six months from now.

    This was less about showing off tricks and more about building trust in the code.

    Why it still matters

    Typing is still one of the primary interfaces between humans and computers. Faster frameworks and flashier tools come and go, but the keyboard remains undefeated. A project like this reinforces how much user experience depends on tiny, cumulative details—milliseconds, characters, edge cases.

    It’s also a reminder that small projects aren’t small achievements. They’re controlled environments where fundamentals get sharpened, instincts get trained, and bad assumptions get quietly corrected.

    Final thoughts

    The 2006 Typing Speed Test isn’t trying to gamify your productivity or rank you against the internet. It’s just a mirror. Sometimes flattering. Sometimes brutal. Always accurate.

    If nothing else, it will teach you one important truth: you type faster when you stop panicking—and slower when you pretend accuracy doesn’t matter. Funny how that works.

    Go ahead. Start the test. The clock’s already waiting.

    Building Time:
    The 2006 Analog Clock Project

    Some projects are about scale. Others are about speed. This one? This one is about precision—the quiet, relentless ticking of logic doing exactly what it’s supposed to do.

    The 2006 Analog Clock Project is a deceptively simple web application that recreates a classic analog clock using modern front-end techniques. No libraries doing the heavy lifting. No shortcuts. Just JavaScript, CSS, and the stubborn belief that understanding fundamentals is never a waste of time. (Unlike meetings that could’ve been emails.)

    Why an Analog Clock?

    Because analog clocks are brutal in the best way.

    They demand:

    • Continuous motion
    • Trigonometry hiding in plain sight
    • Real-time synchronization
    • Visual accuracy down to the degree

    Digital clocks forgive you. Analog clocks expose you.

    This project was an exercise in translating time as data into time as motion—turning hours, minutes, and seconds into rotating hands that never drift, stutter, or lie.

    Under the Hood

    At its core, the clock runs on JavaScript’s Date object, polling the current time and converting it into rotational values.

    Each hand:

    • Seconds rotate at 6° per second
    • Minutes rotate at 6° per minute (with second-based offsets for smooth motion)
    • Hours rotate at 30° per hour (plus minute offsets, because accuracy matters)

    CSS handles the transforms, anchoring each hand at its base so rotations feel natural—no helicopter blades here. Subtle transitions keep motion smooth without introducing lag, because a clock that jitters is existentially unsettling.

    Design Philosophy

    The visual design stays intentionally restrained.

    This isn’t about flashy gradients or glassmorphism flexing for attention. It’s about clarity, contrast, and balance. The face is readable at a glance. The hands are distinct. The clock looks like a clock—an underrated achievement in web design.

    Dark backgrounds were chosen to reduce visual noise and keep focus on motion, reinforcing the idea that time should flow, not shout.

    What This Project Proves

    This project demonstrates:

    • Comfort with JavaScript timing and real-time updates
    • Practical use of CSS transforms and positioning
    • Attention to mathematical detail
    • Respect for classic UI metaphors
    • An understanding that fundamentals scale better than frameworks

    It’s also a reminder that not every portfolio piece needs to be a sprawling app with fifteen dependencies and a build step that could summon ancient spirits.

    Sometimes, mastery looks like restraint.

    Final Thoughts

    The 2006 Analog Clock Project is a quiet project—and that’s its strength. It ticks along faithfully, doing one thing well, every second, without complaint. Honestly? Goals.

    Time is relentless. Code doesn’t have to be.

    And if you can make something as unforgiving as an analog clock behave perfectly in the browser, you’re probably ready for much bigger monsters.

    Next project. Same discipline. Fewer mercy rolls.
